# 구현 작업 인계 템플릿

> 이 파일은 **개발자 또는 코딩 에이전트에게 한 작업을 맡기는 양식**이다. LineMedic 운영 에이전트의 시스템 프롬프트가 아니다. 아래 빈칸을 채우고 관련 문서만 전달한다. 문서 패키지 전체를 한 번에 구현하도록 지시하지 않는다.

## 1. 작업 계약

| 항목 | 입력 |
|---|---|
| 작업 ID | W00~W29 중 W__ 또는 잔여 H__ — [작업표](../docs/10-delivery-plan.md) 참조 |
| 등급 | core / hardening (hardening은 관련 v4 core와 실제 전체 경로 통과 후에만) |
| 목표 시각 (KST) | [10](../docs/10-delivery-plan.md)에서 실제 남은 시간에 맞춰 정한 시각 |
| 실행 모드 | local / sandbox |
| 목표 | 이 작업에서 끝낼 동작 한 가지 |
| 담당 | 미배정 |
| 작업 branch / 기준 commit | 미확인 |
| 이번에 수정 가능한 코드·문서 | 명시적 경로 |
| 수정하면 안 되는 것 | 다른 팀 모듈·보호된 계약·credential 등 |
| 선행 작업의 실제 상태 | 미착수 / 구현 / mock test / live 통합 |
| 사용 환경 | OS·Python·Docker·runtime 실제 값 |
| 시간 제한·중단 기준 | 작업 단위로 작성 |
| 완료 기준 | FR/AC 및 테스트 ID를 기재 |

## 2. 읽을 자료

공통으로 [마스터 플랜](../00-MASTER-PLAN.md), [요구사항](../docs/01-requirements.md), [작업 계획](../docs/10-delivery-plan.md)을 읽는다. 이번 구현과 직접 관계 있는 계약만 추가한다.

- API·auth·상태: [03](../docs/03-api-contracts.md), [04](../docs/04-data-state.md)
- agent·broker: [05](../docs/05-agent-spec.md), [06](../docs/06-broker-runner.md)
- 격리·release·검증: [07](../docs/07-security.md), [08](../docs/08-release-verification.md)
- 시나리오·수용 시험: [09](../docs/09-scenarios-evaluation.md)
- 환경·NVIDIA: [11](../docs/11-runbook.md), [12](../docs/12-nvidia-requirements.md)
- Issue·선점: [15](../docs/15-issue-intake-workflow.md)
- 시작·차단·결과 알림: [16](../docs/16-notifications.md)
- 사례 저장·검색·평가 분리: [17](../docs/17-case-memory.md)
- 기존 코드/DB 전환: [18](../docs/18-migration-validation.md)

작업과 무관한 P1 기능, 새 프레임워크, 범용 추상화, 별도 event bus를 추가하지 않는다. 구현을 위해 공개 계약 수정이 필요하면 먼저 이유와 영향 문서를 제시한다.

## 3. 개발 요청 본문 — 복사 후 빈칸을 채운다

```text
LineMedic v4의 작업 [W__]만 구현하라.

목표:
[관찰 가능한 동작 한 가지]

기준:
[문서 경로·절·FR/AC·테스트 ID]

작업 범위:
- 수정 허용: [경로]
- 수정 금지: [경로]
- 선행 상태: [실제 확인한 내용]

진행:
1. 기존 코드를 읽고 현재 구현·테스트·미구현을 먼저 확인한다.
2. 이 작업의 실패 사례와 수용 시험부터 정의한다.
3. 최소 구현을 하고 허용 범위 안에서 테스트한다.
4. 테스트 실행 여부, 환경 제약, mock/live/manual을 구분한다.
5. 변경 파일, 실행 명령과 결과, 미완료·잔여 위험을 보고한다.

제약:
- 설계 문서의 목표 명령이 이미 구현됐다고 가정하지 않는다.
- 실제 SDK/API 문법과 버전은 설치 환경·공식 문서로 확인한다.
- 키·비공개 로그·runtime state를 저장소에 커밋하지 않는다.
- PR 생성·merge·배포 등 외부 쓰기는 이번 작업에서 명시적으로 허용한
  전용 테스트 자원에만 수행한다. 일반 개발 요청을 운영 변경 승인으로 해석하지 않는다.
- 실패하는 테스트를 지우거나 검증 조건을 약하게 만들어 통과시키지 않는다.
- 실제 agent 작업은 binding·승인·시작 알림 receipt 뒤에만 시작한다.
- Issue 생성·메일 전송 등 쓰기는 명시적으로 허용된 테스트 자원에서만 한다.
- provider timeout을 성공/실패로 추정해 재전송하지 않는다.
- PR 생성·권한 부족·미확인 결과를 검증된 정답/오답으로 기록하지 않는다.
- 이 작업이 막히면 전체 아키텍처를 다시 만들지 말고 최소 차단 요인과 대안을 보고한다.
```

## 4. 보호된 테스트의 의미

운영 LineMedic 에이전트는 보호된 회귀 테스트·업무 계약·평가 기대값을 수정할 수 없다. 개발 담당자는 **해당 계약/테스트를 구현하는 작업을 명시적으로 맡았을 때** 작성할 수 있다. 그러나 구현 완료 후 버그를 감추기 위해 기대값을 바꾸지 않는다. 계약 변경은 사람 검토와 재평가를 필요로 한다.

평가기 holdout과 정답표를 운영 agent workspace로 복사하지 않는다. 개발용 인계 문서를 운영 agent prompt로 통째로 전달하지 않는다.

## 5. 처음 맡길 작업 예시

**W04 → W05**를 먼저 잡으면 실제 서비스와 독립 검증 기준을 동시에 만들 수 있다.

| 구분 | W05 예시 |
|---|---|
| 목표 | `defect-summary-v1`로 정상과 잘못된 HTTP 200을 구분 |
| 선행 | W04의 실제 MES endpoint와 합성 fixture |
| 허용 범위 | verifier 모듈·검증 테스트·계약 초안 |
| 제외 | 모델 호출, PR, 배포 자동화, OpenShell 설치 |
| 수용 | 정상 fixture PASS, 잘못된 total FAIL, 관측 불가 INCONCLUSIVE |
| 증거 | 사용한 source/contract hash, test 출력, 실제 HTTP 실행 기록 |

이 예시는 실제 코드·테스트를 실행했다는 뜻이 아니다. W04가 미구현이면 먼저 그 사실을 확인하고 해당 작업부터 수행한다.

## 6. 완료 보고 양식

### 변경

| 파일 | 변경 이유 | 계약 영향 |
|---|---|---|
| 입력 | 입력 | 없음 / 문서 수정 |

### 검증

| 시험 ID | 명령 또는 호출 | 환경 | 결과 | 증거 경로 |
|---|---|---|---|---|
| 입력 | 실제 실행한 내용 | mock/live/manual | PASS/FAIL/NOT_RUN | 입력 |

### 미완료·주의사항

수행하지 못한 시험과 이유, 필요한 외부 권한, 다음 작업이 의존하는 미완료 부분을 적는다. 단위 테스트 성공을 전체 agent E2E 성공으로 표시하지 않는다.

### 인계

다음 W 작업 ID와 전달할 API·artifact·고정 버전을 적는다. ‘백그라운드에서 계속 진행’이라고 약속하지 않고, 현재 수행한 결과만 기록한다.
