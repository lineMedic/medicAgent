# 13. 최소 화면·발표·제출 명세 v4

> 구현 전 예시다. 실제 실행하지 않은 흐름·채널·모델·검색 엔진을 사용 완료로 표시하지 않는다. 제품의 핵심은 ‘정확한 Issue에서 시작을 알리고, 맞는 범위에서 일하며, 검증된 결과를 다음 작업에 남긴다’이다.

## 1. 화면 하나

상단에 run ID, 실제 호스트·runtime·sandbox 상태, 모델, memory mode/snapshot, repo와 polling 마지막 성공 시각을 표시한다. 본문은 현재 Issue/work 카드와 타임라인, 오른쪽은 근거·case note를 둔다.

```text
Issue #42 · WORK-001/g1 · INC-001 · mes-api
티켓 연결: 기존 Issue 재사용 / match basis=OPERATOR
작업: WAITING_REVIEW               업무: 아직 미검증
알림: 시작 댓글 접수됨 #comment-1    메일 전달: 사용하지 않음
기억: memory_assisted / snapshot MEM-001 / 관련 사례 2건

[Issue 연결] → [시작 알림 접수] → [agent 시작] → [사례/현재 근거 조회]
 → [테스트·패치 검사] → [PR #51] → [사람 승인 대기]

사례 CASE-OLD-01: VERIFIED_FAILURE, HTTP200이지만 집계가 틀림
사례 CASE-OLD-02: BLOCKED, 당시 권한 부족 — 현재도 틀린 패치라는 뜻 아님
```

위 ID와 내용은 형식 예시다. 실제 화면은 DB read model로 채운다. native thought 전체 대신 도구·근거·짧은 판단 요약을 표시한다. Issue·로그·case 본문은 HTML escaping하며 임의 링크를 자동 호출하지 않는다.

## 2. 상태 문구

| 저장 상태 | 표시 | 금지 표현 |
|---|---|---|
| work WAITING_APPROVAL | 처리 범위 승인 대기 | 자동 처리 시작 |
| WAITING_NOTIFICATION | 시작 알림 확인 대기, 수정 미시작 | 작업 중 |
| RUNNING | 원인 조사·수정안 작성 중 | 복구됨 |
| WAITING_REVIEW / incident PR_OPENED | PR 준비, 사람 리뷰·배포 승인 필요 | 자동 복구 완료 |
| HANDED_OFF / WORK_ORDER_DRAFTED | 정비 요청 초안·담당자 확인 필요 | 정비 완료 |
| BLOCKED / ESCALATED | 진행 불가, 사유와 필요한 조치 | 실패 원인 없이 단순 오류 |
| EXECUTION_UNKNOWN | 외부 조치 여부 미확인 | 실패했으니 재실행 |
| RESOLVED / SUCCEEDED | 지정한 업무 계약·관찰 범위 통과 | 모든 장애 해결 |
| notification ACCEPTED | 댓글 등록 / 메일 서버 접수 | 사람이 읽음 |
| case UNVERIFIED | 아직 업무 검증 없는 시도 | 정답 사례 |

## 3. 시연 구성

S1에서 로그가 들어오면 먼저 기존 Issue를 찾거나 새 Issue를 만든다. 수정 전 시작 알림을 보여주고, actual agent가 코드를 조사한다. 같은 증상이 이미 등록됐을 때 번호를 재사용하고, bot 댓글이 추가돼도 작업이 반복되지 않는 것을 보여준다.

S2-lite는 Issue를 받았지만 서버를 수정하지 않고 카메라 지표와 미확인 원인을 남긴다. 이는 작업 회피가 아니라 다른 담당자에게 필요한 정보를 전달한 결과다. 실제 현장 조치는 제공하지 않는다.

S1b는 verifier가 잘못된 HTTP200을 거절한다. 실패 case로 저장되더라도 사람이 만든 결함임을 표시한다. S7은 그 노트가 다음 memory_assisted 조사에 검색되는 장면이다. 당시 오답 조건을 읽고 현재 데이터로 다시 검사한다.

S6에서는 지원 밖 DB 변경이나 권한 부족을 넣어 ‘무엇이 필요한지’가 적힌 외부 알림을 보여준다. 창의성은 단순 ticket 생성 자체가 아니라, **코드/설비/불가 분기와 검증 수준별 재사용**의 결합에서 설명한다. 시장 전체의 최초·경쟁 제품 부재를 주장하지 않는다.

## 4. 3분 영상 예시

| 구간 | 장면 | 핵심 문장 |
|---|---|---|
| 0:00~0:20 | 업무 장애와 이미 열린 Issue | ‘로그와 티켓이 따로 놀면 같은 조사가 반복됩니다.’ — 문제 가설 |
| 0:20~0:40 | 기존 Issue 연결·시작 댓글 | ‘새 작업을 중복 만들지 않고 시작을 먼저 알립니다.’ |
| 0:40~1:25 | sandbox agent·과거 실패 근거·현재 코드·PR | ‘과거 기록은 참고하고, 지금 코드에서 재현·검사합니다.’ |
| 1:25~1:50 | 사람 승인·exact image·업무 검사 | ‘PR과 머지가 아니라 실제 업무 결과로 확인합니다.’ |
| 1:50~2:10 | 설비 분기 또는 불가 보고 | ‘코드로 해결할 수 없으면 범위를 넘지 않고 이유를 전달합니다.’ |
| 2:10~2:30 | 잘못된200·case 노트 | ‘성공과 실패, 권한 부족을 다른 종류의 기록으로 남깁니다.’ |
| 2:30~2:45 | S3 독립 보호 시험 | ‘이 시험에서 확인된 경계와 미확인 범위를 구분합니다.’ |
| 2:45~3:00 | actual 평가 수·cold/memory 구분 | ‘실패와 수동 개입까지 함께 공개합니다.’ |

압축 편집은 가능하지만 생략한 사람 승인·대기 시간을 무인 즉시 처리처럼 보이게 하지 않는다. 모든 장면을 한 번의 live run처럼 조합하지 않는다. 공식 영상 길이 R4가 우선이다.

## 5. 신청서 초안

아래는 **구현이 완료된 부분만 남겨 제출할 초안**이다. 글자 수는 최종 폼 기준으로 다시 확인한다.

### Problem Definition

> 공장 IT 장애 대응에서 로그, GitHub 이슈, 수정 이력이 분리돼 있으면 같은 오류를 중복 조사하거나 이미 진행 중인 작업과 충돌할 수 있습니다. AI가 수정안을 만들어도 코드와 설비 중 어디를 확인해야 하는지, 실제 업무가 복구됐는지, 해결하지 못한 이유가 무엇인지 전달돼야 합니다. 과거의 실패를 성공 사례처럼 재사용하지 않는 대응 기록도 필요합니다. LineMedic은 이 문제를 합성 MES·설비 시뮬레이터에서 검증합니다.

### Solution

> LineMedic은 로그와 등록된 GitHub Issue를 단일 작업으로 연결합니다. 대응 이슈가 있으면 재사용하고, 없으면 생성한 뒤 작업 시작을 알립니다. Nemotron 에이전트는 현재 로그·코드·설비 지표와 허용된 과거 사례를 조회해 코드 수정, 설비 점검 요청 초안, 진행 불가 보고를 구분합니다. 수정안은 격리된 검사와 사람 리뷰·배포 승인을 거치며, 독립 업무 검증을 통과해야 복구로 기록합니다. 결과는 검증된 성공·실패·미확인·권한 차단으로 구분해 다음 조사에 활용합니다. 에이전트는 OpenShell 경계 안에서 동작하며 실제 PLC 제어와 자동 머지는 하지 않습니다.

### Tech Stack 기입 규칙

실제 사용한 모델 ID·endpoint·runtime·OpenShell 정책과 버전을 적는다. NAT/Guardrails는 실제 경로에서 쓴 경우만 적는다. SQLite lexical 검색을 NVIDIA embedding 또는 vector RAG라고 표현하지 않는다. core가 GitHub 댓글만 쓰면 ‘메일 발송’이라고 쓰지 않는다. 온프레미스 NIM은 실제 실행 전에는 계획이다.

## 6. 심사 기준에 대응하는 증거

| 항목 | 실제 제출 근거 |
|---|---|
| NVIDIA Agent 활용 심도 | 실제 sandbox runtime, Nemotron 도구 선택, 선택한 NAT trace·보호 기능 |
| 실용성·산업가치·혁신 | Issue 재사용·시작 알림·불가 전달·코드/설비 분기·검증된 사례 reuse |
| 완성도 | actual Issue+notification+agent+검증·실패 분기, reset·재현 |
| 커스터마이징·독창성 | 업무 계약, 성공/오답/차단 노트 분리, 권한·버전·근거 기반 처리 |

단순 Github 연동·RAG 추가만으로 높은 점수가 보장된다고 말하지 않는다. 평가 항목별 배점과 대회 인정은 주최 측 원문을 기준으로 한다.

## 7. 예상 질문

**Issue가 이미 있으면 어떻게 하나요?** 확정 binding 또는 승인된 대응을 재사용합니다. 제목만 비슷하면 후보를 제시하고 임의로 같은 문제라고 결정하지 않습니다.

**아무나 Issue를 만들면 코드를 고치나요?** 등록 repo와 사전 승인한 작성자/작업 범위만 자동 처리합니다. 미승인 요구와 진행 중인 사람 작업은 대기·이관합니다.

**알림을 보내지 못하면요?** 시작 알림은 접수 확인 전 코드를 작성하지 않습니다. 완료 알림 실패는 이미 확인한 업무 검사 결과와 별도로 기록합니다. 공급자 장애에서 전달됐다고 말하지 않습니다.

**RAG가 모델을 학습시키나요?** 아닙니다. 저장된 사례를 검색해 현재 조사 문맥에 제공하고 다시 검증합니다. cold_start와 memory_assisted 결과를 구분합니다.

**오답노트는 어떻게 정하나요?** 실제 업무 검사 실패는 오답 사례, 권한 부족은 차단 사례, PR-only는 미검증 사례입니다. 모델이 성공이라고 말한 것을 정답으로 저장하지 않습니다.

**샌드박스만 있으면 안전한가요?** agent뿐 아니라 generated test/patch와 배포 MES를 비신뢰 대상으로 제한합니다. 시험한 경계가 모든 공격·호스트 침해를 막는다는 뜻은 아닙니다.

## 8. 제출 점검

- [ ] S1/S2-lite/S1b/S3/S4~S7 중 실제 완료·미실행을 구분했다.
- [ ] Issue 존재 확인·시작 receipt·attempt 시각·PR·검사 identity가 연결된다.
- [ ] 이메일/댓글 접수·사람 수신/열람을 혼동하지 않았다.
- [ ] actual case origin·snapshot·검색 엔진·cold/memory 분모를 명시했다.
- [ ] 사람 패치·승인·배포·S1b를 무인 agent 성과로 합산하지 않았다.
- [ ] 실제 실행하지 않은 NVIDIA 제품·온프레미스·메일 채널을 사용이라고 적지 않았다.
- [ ] 회사·고객 데이터 없이 합성 환경임을 밝혔다.
- [ ] R1~R5의 원문·답변 또는 미확인 상태를 보존했다.
- [ ] 팀원 개별 제출·영상 길이·저장소 접근은 확정 조건에 맞췄다.
