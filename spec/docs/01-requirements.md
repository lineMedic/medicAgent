# 01. 요구사항과 수용 기준

> v4 규범 문서. 이 파일은 **무엇을 구현하면 완료인지**를 정의한다. v4는 요구사항을 `[core]`(반드시 완료)와 `[hardening]`(core 완료 후, 미완료 시 `설계됨/미구현` 공개)으로 나눈다. API는 [03](03-api-contracts.md), 상태는 [04](04-data-state.md)가 기준이다.

## 1. 사용자와 사용 범위

| 사용자 | 필요한 결과 | 제품이 대신하지 않는 일 |
|---|---|---|
| 개발자·IT 당직 | 증거, 재현 테스트, 최소 패치, 검사 결과 | 변경 승인과 원인 해석 최종 책임 |
| 정비 담당 | 설비 ID·관찰 지표·미확인 원인이 있는 요청 초안 | 실제 설비 점검·작업 안전 절차 |
| 데모 운영자 | 장애 주입, 정확한 릴리스 선택, 반복 평가 | 모델 답변을 사후 편집해서 성공 만들기 |
| 평가자 | 원본 실행, 실패, 코드·이미지·정책 버전 | 실제 공장 성능·보안 인증으로 확대 해석 |

예선 입력은 합성 로그·fixture·가짜 카메라 지표와 팀 소유 GitHub 저장소의 승인된 Issue다. 사용자의 회사 시스템에 연결하거나 비밀·개인정보를 가져오지 않는다.

## 2. 기능 요구사항

| ID | 요구사항 | 등급 | 수용 기준 |
|---|---|---|---|
| FR-01 | 장애를 감지하고 같은 사건을 묶는다 | core | 같은 run·fingerprint의 미해결 사건은 하나, 재디스패치 없음 |
| FR-02 | 시간·서비스·run이 연결된 증거를 저장한다 | core | 각 조회 결과에 증거 ID와 관찰 시각, 출처가 있음 |
| FR-03 | 모델이 조회 도구를 선택하고 제안한다 | core | 최소 1건의 실제 모델 tool-call 왕복과 최종 구조화 제안 |
| FR-04 | 코드 문제의 패치·재현 테스트를 만든다 | core | S1에서 실제 에이전트 산출물이 고정 base에 적용됨 |
| FR-05 | 브로커가 원본 산출물을 검사한다 | core | 경로·내용·테스트·기준 커밋·권한 검사를 통과해야 PR 가능 |
| FR-06 | 검토용 PR을 생성한다 | core | 봇 계정(GitHub App 또는 전용 계정)이 지정 저장소·기준 브랜치에만 생성, 다른 사람이 리뷰, 자동 머지 없음 |
| FR-07 | 승인된 정확한 코드만 배포한다 | core | merge SHA 재검사, 이미지 ID 기록, 실제 실행 이미지 일치 |
| FR-08 | 업무 결과로 복구를 판정한다 | core | 4회 샘플·60초 관찰·데이터/버전 일치 후 검증기만 `RESOLVED` |
| FR-09 | 설비 점검 요청 초안을 만든다 | core | S2-lite에서 등록 설비·증거·가설·승인된 참조를 기록, 코드 변경 없음 |
| FR-10 | 거짓 정상 응답을 거절한다 | core | S1b의 HTTP 200·틀린 집계에 `content_mismatch` |
| FR-11 | 안전 경계와 실패 처리를 시험한다 | core | 금지 조치·권한·timeout 시 `EXECUTION_UNKNOWN` 기록·중복 논리 키·S3 결과를 각자 기록 |
| FR-12 | 모든 실행을 재현·보존한다 | core | 초기화로 원격 이력·기존 평가가 지워지지 않음 |
| FR-13 | 상태·근거·변경·검사 결과를 표시한다 | core 최소판 | UI가 DB를 읽음. 모르는 값은 미확인으로 표시 |
| FR-14 | 실제 NVIDIA 사용·대회 인정 상태를 명시한다 | core | 사용 버전과 성공 호출, 조건 R1~R5의 확인 상태 기록 |
| FR-15 | 에이전트를 OpenShell 샌드박스 안에서 실행한다 | core | S1·S2-lite 평가 실행의 agent mode가 `sandbox`, 정책 hash와 샌드박스 identity 기록 |
| FR-16 | 모든 평가를 한 데모 호스트에서 실행한다 | core | 호스트 manifest(OS·arch·Docker·런타임·OpenShell 버전)를 모든 run에 연결 |

### v4 추가 core 요구사항

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-17 | 로그를 등록 repo의 기존 Issue에 연결하고 없으면 생성 | 조회 범위·완전성 기록, 확정 매칭/사람 연결, 생성 receipt와 binding 저장. 모호함·조회 오류에서 신규 생성 금지 |
| FR-18 | 새 GitHub Issue를 자동 접수 | opt-in repo·승인된 actor·범위 검사 후 주기적 접수. 기존 backlog는 기본 자동 시작 금지 |
| FR-19 | 두 입력이 같은 작업을 중복 시작하지 않음 | `(routing_scope, repo, issue)`당 활성 work 하나, atomic claim 경합 시험, 중복 이벤트 재생 시험 |
| FR-20 | 작업 전 외부 알림 | 필수 시작 알림의 provider receipt를 저장한 뒤에만 writable workspace와 agent attempt 시작 |
| FR-21 | 실행 불가 사유 정리·전달 | 구조화된 blocker report, 실제 채널의 접수 결과·재시도 상태. 모델 실패 때도 고정 템플릿으로 보고 |
| FR-22 | 시도·오류·변경·결과를 case note로 저장 | verifier PASS, 의미적 실패, 권한 차단, 미검증을 구별. 원본 evidence·SHA·contract·origin 연결 |
| FR-23 | 현재 작업에 이전 사례 검색·제공 | repo/서비스/시각/공유범위 필터 후 exact+키워드 조회, 결과 ID 인용, no-hit와 검색 불가 구분 |
| FR-24 | 단계별 결과 알림과 상태 일치 | PR_READY·WORK_BLOCKED·HANDOFF_DRAFTED·RECOVERY_VERIFIED 각각 다른 메시지. 알림 성공과 복구 성공 독립 |
| FR-25 | 명시적 재시도·취소·재발 정책 | 닫힌 Issue와 사람 진행 작업을 강탈하지 않음. 실패 attempt 자동 무한 재실행 금지, 재시도 승인 시 새 generation |
| FR-26 | 외부 부작용과 기억 평가의 신뢰성 | 같은 멱등키 다른 본문 409, UNKNOWN 재실행 금지, cold_start/memory_assisted 분리 |

## 4. 엔드투엔드 수용 시나리오

### AC-S1: 코드 수정 경로

**Given** 고정된 버그 base SHA, 검사자 누락 로트, 정상 회귀 로트, 새로운 demo run.  
**When** 기존/신규 Issue를 연결하고 시작 알림 receipt를 확보한 뒤 실제 에이전트가 조사해 테스트·패치를 제안하고 브로커가 검증한 뒤 사람이 PR을 검토·머지하고 해당 merge SHA 배포를 승인한다.  
**Then** 승인한 코드·실행 이미지·업무 검사 결과가 연결되고 모든 계약과 관찰 조건을 만족할 때만 `RESOLVED`다.

사람이 패치를 대신 작성하거나 에이전트 결과를 사후 수정하면 `human-authored` 또는 `human-edited` 실행으로 별도 분류한다.

### AC-S2: 설비 분기

**Given** 카메라 2번의 밝기·신뢰도 이상과 다른 카메라의 정상 지표. 최근 배포는 있어도 직접 원인이라는 증거가 없다.  
**When** 에이전트가 관련 자료를 조회한다.  
**Then** 정비 요청 초안을 남기고 서버 패치·재시작·배포·정비 완료 처리를 하지 않는다. 렌즈 오염 등 세부 원인은 가설로 표시한다.

### AC-S1B: 잘못된 200

**Given** 팀이 만든 오류 집계 응답(7을 기대하지만 0 반환)과 `defect-summary-v1`.  
**When** 업무 검증기를 실행한다.  
**Then** `FAIL/content_mismatch`, 사건은 `ESCALATED`이고 복구 성공 집계에 포함되지 않는다. 이 실행은 에이전트 성능 시험이 아니다.

### AC-SBX: 샌드박스 안 실행

**Given** V4-CP0에서 확인한 런타임과 OpenShell 정책, 확정된 데모 호스트.
**When** S1·S2-lite 평가 실행을 시작한다.
**Then** 에이전트 프로세스가 샌드박스 안에서 실행되고, 도구 API와 추론 경로만 성공하며, 실행 기록에 `agent_mode=sandbox`·정책 hash·샌드박스 identity가 남는다. local 모드 실행은 별도로 집계한다.

### AC-S3: 경계 시험

**Given** 팀 소유 모의 수신 서버와, 호스트에서 같은 요청이 도달함을 확인한 대조 결과.  
**When** 로그 인젝션, 브로커 금지 제안, sandbox 허용·거절 프로브를 각각 실행한다.  
**Then** 각 계층의 관찰 결과와 제한을 분리한다. 접속 불가를 곧바로 정책 차단으로 판정하지 않는다.

### AC-S4: 로그에서 Issue 신규/재사용

등록 repo의 모든 조회 페이지가 확인된 범위에서 후보가 없으면 Issue를 생성하고 연결한다. 기존 binding이 있으면 해당 Issue를 재조회해 재사용한다. 제목만 유사하거나 후보가 여럿이면 승인 전 대기한다. rate limit·권한 오류·페이지 상한으로 조회가 불완전하면 '없음'으로 처리하지 않는다.

### AC-S5: Issue 감시·시작 알림·중복

자동 처리에 동의한 repo에서 승인된 작성자가 만든 새 Issue 하나를 감지한다. 같은 Issue의 중복 poll·bot 댓글·동시 로그에도 work와 시작 알림은 하나다. 시작 댓글 receipt 이전에는 agent attempt가 없다. 미승인 작성자나 기존 사람 작업은 자동으로 수정하지 않는다.

### AC-S6: 불가 보고

지원 밖 DB 변경, 부족한 자료, 보호 기능 오류, 논리 모순, 조사 예산 소진을 각각 이유 코드로 구분한다. 무변경 또는 이미 발생한 변경 범위를 포함한 보고서를 저장하고 설정된 채널로 전달한다. 공급자가 확인되지 않으면 PENDING/UNKNOWN으로 남기고 발송됐다고 표시하지 않는다.

### AC-S7: 사례 재사용

이전 실행의 검증 성공·업무 검사 실패·권한 차단을 저장한다. 새로운 memory_assisted run에서 관련 사례를 검색하고 원문 ID·실패 조건을 받는다. 테스트만 통과한 PR은 VERIFIED_SUCCESS가 아니고, 권한 오류는 '틀린 패치'가 아니다. 현재 작업은 다시 검사하며 cold_start 비교에는 사례를 주지 않는다.

## 5. 비기능 요구사항: 초기 설계값

수치는 운영 SLA가 아니라 예선용 상한이다. 변경 시 configuration hash를 바꾸고 평가를 구분한다.

| 항목 | 초기값 |
|---|---|
| 동시 활성 에이전트 작업 | 1 |
| 조사 예산 | 240초, 도구 실행 15회. 전송 재시도는 별도 HTTP 계수 |
| 제안 수정 | 1회, 원래 조사 deadline 유지 |
| 모델 일시 오류 | 같은 예산 안에서 1회 재시도 |
| 로그 조회 | 사건 ±30분, 최대 20줄, 응답 최대 64 KiB |
| 제안 본문 | 최대 128 KiB, UTF-8 JSON |
| 패치 | 업무 파일 1개 수정 + 신규 재현 테스트 1개, 총 변경 100줄 이하 |
| 러너 | 단계당 60초, 1 CPU, 512 MiB, PID 64, 결과 최대 1 MiB |
| 업무 검증 | t=0/10/20/30초 4회, 관찰 종료 t=60초 |
| 네트워크 호출 timeout | 조회 10초, 모델은 조사 deadline 내 별도 설정 |
| 날짜·시각 | 저장은 UTC RFC3339, 화면은 KST 변환 |
| Issue 감시 | 초기 60초, repo 1개, GitHub 권고 대기·rate limit 우선 |
| Issue 조회 상한 | 100건/페이지, 10페이지 초기값. cap 도달로 잔여 페이지가 있으면 INCOMPLETE |
| 사례 검색 | top_k 최대 5, 원문 snippet 각 2,000자, repo·서비스·snapshot 필터 |
| 알림 | 기본 github_comment 1개 필수 route, 실패는 durable outbox |
| 수정 시작 대기 | 시작 알림 60초 초기 대기 한도. 초과 시 차단 보고, 코드 작업 없음 |

## 6. 완료가 아닌 것

문서만 존재, mock API만 성공, 사람이 쓴 패치만 성공, local 모드만 성공, PR만 생성, 컨테이너만 healthy, 샌드박스 프로브만 성공, 기술 로고만 표시, 대회 인정 문의만 전송한 상태는 전체 완료가 아니다. 각 단계 성과는 그대로 기록하되 최종 주장과 구분한다.

Issue 링크 없이 패치부터 생성, 로컬 알림 이벤트만 저장, 과거 로그 파일만 쌓고 검색하지 않음, 정답/오답을 LLM 자기보고로 분류한 상태도 v4 완료가 아니다.
